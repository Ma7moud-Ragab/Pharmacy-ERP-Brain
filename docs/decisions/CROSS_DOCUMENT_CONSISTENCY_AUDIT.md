## Deliverable 1 — Executive verdict

**CONDITIONAL GO.** The team can continue bounded, mock-first exploration, but should not start parallel implementation against the current database, event, or approval contracts. There are unresolved conflicts in the selected schema, date ownership, sales synchronization, recommendation inputs, approval authentication, event tracing, cadence/model scope, and several business rules. The machine-readable contract kit that would let teams build independently is absent. The database generator and DDL are internally consistent at static level, but have not been run against PostgreSQL 16.

The smallest gates before cross-team implementation are: (1) select and align one schema/dataflow baseline, (2) settle the listed contract blockers with the ERP/Identity owners, (3) check in machine-readable contracts and shared fixtures, and (4) execute the selected migrations and critical boundary tests. A final-looking Markdown specification is not runtime evidence.

## Deliverable 3 — Authoritative MVP contract summary

The following reflects the current precedence file. Items labeled **UNRESOLVED** are gaps or conflicts; this summary does not silently settle them.

- **Architecture:** .NET modular-monolith ERP owns `erp_db`; Python/FastAPI Brain owns `brain_db`; the ERP's in-process adapter is the only business-data bridge; transactional outbox events go to Redis Streams. Brain persists normalized and derived intelligence, not ERP truth. No direct Brain-to-`erp_db` connection.
- **Tenant:** one seeded tenant, one demo store, product/business-date sales grain. Pass tenant explicitly from verified identity/job/event context. Do not claim tenant administration, RLS, or production multi-tenant isolation.
- **Canonical API:** the MVP file lists product, inventory and supplier reads; sales reads with cursor; open-PO reads; draft PO create; Brain insights and per-product forecasts. Product IDs are UUIDs; SKU is descriptive. Quantities use canonical product units. Amount and currency are optional; demand is units. **UNRESOLVED:** detailed request/response schemas, page ordering and snapshot semantics, PO status/open definition, actual Backend capability/sign-off, and some route/response shape differences.
- **Events:** ERP outbox row commits in the business transaction; Redis delivers duplicates/out of order; event effects plus `(tenant_id,event_id)` dedupe commit atomically before `XACK`. This is at-least-once delivery with idempotent database effects, never exactly-once Redis delivery. Sale events carry UUID IDs, lines, ERP business date, UTC `occurred_at`, optional money fields. **UNRESOLVED:** trace field format, schema major/minor behavior, aggregate version fields, duplicate ID/different payload response in the wire contract, and complete event set.
- **Sync/reconciliation:** Canonical reads/backfill are the completeness mechanism. Closed-day totals are overwritten from authoritative canonical totals; incomplete dates are excluded from training and never silently zero-filled. **UNRESOLVED:** inclusive/exclusive `updated_since`, high-watermark/snapshot visibility, stable cursor ordering, overlap and correction/status semantics. Redis alone cannot prove completeness.
- **Features/forecasting:** grain is `(tenant, product, business_date)`. Only verified complete days are observations; complete days with no sales may be zero-filled. Training and inference share a strict, ordered, versioned feature contract with labels excluded from inputs. Forecast generations are append-only, versioned and carry quality flags. Deterministic baseline plus one classical path is the stated MVP scope. **UNRESOLVED:** chosen model family, serving/retraining cadence, stockout censoring source, and cold-start policy alignment.
- **Risk/recommendation:** deterministic versioned rules; require current inventory, preferred supplier, lead time and open-PO information before suggesting a PO. Emit a stable unavailable reason instead of assuming missing data is zero. Anomaly review workflow is out of scope. **UNRESOLVED:** exact seeded rule values and order quantity formula; live versus cached PO freshness; stale-data cutoff.
- **Agent:** only `create_purchase_order` writes, and it creates a draft. Proposal arguments are immutable; human approval with `agent:approve` binds to the exact hash; execute the exact approved payload with the same idempotency key; reject/expire never calls ERP; timeout recovery must not duplicate a PO. **UNRESOLVED:** token/OBO transport, whether requester can self-approve, hash canonicalization, ERP idempotency retention, and 4-hour versus 24-hour proposal TTL.
- **LLM:** provider-neutral hosted service for on-demand explanation/assistant requests after deterministic/classical processing; no arithmetic, SQL, direct ERP access, PII or raw tables. Record provider/model/usage/latency/cost, not prompt/completion text. Embeddings, RAG and pgvector are out of MVP.
- **Security/retention/observability:** JWT-derived identity/tenant/scopes; error envelope and `traceparent` on HTTP calls; audit and proposal records retained without MVP deletion; agent message content 30 days; session expires after 4 idle hours. **UNRESOLVED:** service identity and OBO flow, event trace representation, log/audit integrity extensions and legal retention policy before production.
